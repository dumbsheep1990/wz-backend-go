# WZ项目DDD架构设计文档 - 530


## 📐 架构设计原则

### 1. 领域驱动设计 (DDD) 核心原则
- **业务第一**: 代码结构直接反映业务概念
- **充血模型**: 实体包含业务行为，而非仅数据载体
- **聚合边界**: 明确一致性和事务边界
- **通用语言**: 代码与业务术语保持一致

### 2. 分层架构设计
```
┌─────────────────────────────────────┐
│            接口层 (Interfaces)        │ ← HTTP/gRPC/Event Handlers
├─────────────────────────────────────┤
│            应用层 (Application)       │ ← 用例编排、DTO转换、事务管理
├─────────────────────────────────────┤
│            领域层 (Domain)           │ ← 业务逻辑、实体、值对象、领域服务
├─────────────────────────────────────┤
│          基础设施层 (Infrastructure)   │ ← 数据库、消息队列、外部服务
└─────────────────────────────────────┘
```

## 🧱 核心组件设计

### 1. 值对象 (Value Objects)

#### 设计模式
```go
// 标准值对象模板
type {Concept}ID struct {
    value string
}

func New{Concept}ID(value string) ({Concept}ID, error) {
    if err := validate{Concept}ID(value); err != nil {
        return {Concept}ID{}, err
    }
    return {Concept}ID{value: value}, nil
}

func (id {Concept}ID) Value() string { return id.value }
func (id {Concept}ID) IsEmpty() bool { return id.value == "" }
func (id {Concept}ID) Equals(other {Concept}ID) bool { return id.value == other.value }
```

#### 已实现的值对象类型
| 值对象类别 | 实现示例 | 验证规则 |
|------------|----------|----------|
| ID类型 | `SiteID`, `UserID`, `ProductID` | 非空，长度限制 |
| 名称类型 | `SiteName`, `Username`, `ProductName` | 非空，长度范围，格式验证 |
| 状态类型 | `SiteStatus`, `UserStatus`, `OrderStatus` | 枚举值验证，状态转换规则 |
| 业务规则 | `Domain`, `Email`, `Money` | 复杂格式验证，业务规则 |

### 2. 实体和聚合根 (Entities & Aggregates)

#### 聚合根设计模式
```go
type {Aggregate} struct {
    // 私有字段，通过方法访问
    id          valueobject.{Aggregate}ID
    name        valueobject.{Aggregate}Name
    status      valueobject.{Aggregate}Status
    // ... 其他业务字段
    
    // 时间戳
    createdAt   time.Time
    updatedAt   time.Time
    
    // 领域事件
    domainEvents []event.DomainEvent
}

// 工厂方法
func New{Aggregate}(...) (*{Aggregate}, error) {
    // 业务验证
    // 对象构造
    // 发布创建事件
}

// 业务行为方法
func (a *{Aggregate}) {BusinessOperation}(...) error {
    // 业务逻辑验证
    // 状态变更
    // 发布领域事件
}
```

#### 聚合设计原则
- **一致性边界**: 每个聚合确保内部一致性
- **最小化聚合**: 只包含必要的实体
- **ID引用**: 聚合间通过ID引用，避免对象引用
- **事务边界**: 一个事务只能修改一个聚合

### 3. 领域事件 (Domain Events)

#### 事件设计模式
```go
type {Aggregate}{Action}Event struct {
    AggregateID string    `json:"aggregate_id"`
    // ... 事件相关数据
    OccurredAt  time.Time `json:"occurred_at"`
}

func (e {Aggregate}{Action}Event) GetAggregateID() string { return e.AggregateID }
func (e {Aggregate}{Action}Event) GetEventType() string { return "{aggregate}.{action}" }
func (e {Aggregate}{Action}Event) GetOccurredAt() time.Time { return e.OccurredAt }
func (e {Aggregate}{Action}Event) GetEventData() interface{} { return e }
```

#### 事件类别
| 事件类型 | 命名规则 | 用途 |
|----------|----------|------|
| 创建事件 | `{Aggregate}CreatedEvent` | 聚合创建时发布 |
| 更新事件 | `{Aggregate}UpdatedEvent` | 属性变更时发布 |
| 状态事件 | `{Aggregate}{Status}Event` | 状态转换时发布 |
| 业务事件 | `{Aggregate}{BusinessAction}Event` | 关键业务动作时发布 |

### 4. 仓储接口 (Repository Interfaces)

#### 仓储设计模式
```go
type {Aggregate}Repository interface {
    // 基本CRUD
    Save(ctx context.Context, aggregate *entity.{Aggregate}) error
    FindByID(ctx context.Context, id valueobject.{Aggregate}ID) (*entity.{Aggregate}, error)
    Delete(ctx context.Context, id valueobject.{Aggregate}ID) error
    
    // 业务查询
    FindBy{BusinessCriteria}(ctx context.Context, criteria {Criteria}) ([]*entity.{Aggregate}, error)
    
    // 存在性检查
    ExistsBy{Criteria}(ctx context.Context, criteria {Criteria}) (bool, error)
    
    // 计数和分页
    Count(ctx context.Context, filters {Filters}) (int64, error)
}
```

## 🎯 设计决策记录

### 1. 聚合边界设计决策

#### 站点聚合边界
**决策**: 将Page作为Site聚合的一部分，而非独立聚合
**理由**:
- 页面与站点有强一致性要求
- 首页设置需要在站点级别保证唯一性
- 页面的生命周期依赖于站点

#### 订单聚合边界
**决策**: Order、OrderItem、OrderDiscount在同一聚合内
**理由**:
- 订单金额计算需要保证一致性
- 订单项变更影响整个订单状态
- 折扣规则应用需要原子性

### 2. 值对象粒度设计

#### 粗粒度值对象: ThemeConfig
```go
type ThemeConfig struct {
    primaryColor    string
    secondaryColor  string
    accentColor     string
    // ... 其他主题属性
}
```
**优点**: 减少参数传递，封装相关概念
**缺点**: 变更时影响面较大

#### 细粒度值对象: 单一概念
```go
type SiteID struct { value string }
type SiteName struct { value string }
```
**优点**: 单一职责，变更影响小
**缺点**: 可能导致参数过多

### 3. 事件发布策略

#### 同步发布 (当前实现)
```go
// 在事务内同步发布事件
for _, event := range aggregate.GetDomainEvents() {
    if err := s.eventBus.Publish(ctx, event); err != nil {
        return err  // 事务回滚
    }
}
```

#### 异步发布 (未来优化)
```go
// 事务提交后异步发布
defer func() {
    for _, event := range events {
        s.eventBus.PublishAsync(event)
    }
}()
```

## 📊 性能与扩展性考量

### 1. 查询优化

#### CQRS模式应用
- **命令端**: 使用DDD聚合保证一致性
- **查询端**: 使用优化的查询模型和视图

#### 读写分离
```go
// 写操作：通过聚合
func (s *SiteApplicationService) UpdateSite(ctx context.Context, req UpdateSiteRequest) error

// 读操作：直接查询优化
func (s *SiteQueryService) GetSiteListView(ctx context.Context, filters SiteFilters) (*SiteListView, error)
```

### 2. 缓存策略

#### 聚合缓存
```go
// 缓存整个聚合
cache.Set(fmt.Sprintf("site:%s", siteID), site, 1*time.Hour)
```

#### 查询结果缓存
```go
// 缓存查询结果
cache.Set(fmt.Sprintf("sites:tenant:%s", tenantID), sites, 30*time.Minute)
```

### 3. 事件处理性能

#### 批量事件处理
```go
// 批量发布事件，减少IO开销
eventBus.PublishBatch(ctx, events)
```

#### 异步事件处理
```go
// 异步处理非关键事件
go eventHandler.HandleAsync(event)
```
